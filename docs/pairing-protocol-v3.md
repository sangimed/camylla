# M4 production pairing and authenticated sessions (proposed v3)

Status: reviewed design for #24, implemented on the #25 feature branch. Normal Android/desktop operation uses v3; v2 development credentials require the explicit CLI development mode. Physical rotation validation is still pending. See `validation/android-windows-m4-4.md` for the exact evidence and remaining gates. This document defines a new major version because a v2 peer must fail closed rather than silently accept a production peer with different authentication.

## Roles, identities, and cryptography

The Android phone initiates pairing and every capture session. The Windows user process listens on control TCP 58413 and video TCP 58414; the virtual-camera DLL never accepts network connections. Discovery and addresses are routing hints, never authorization. TLS 1.3 is required for v3; no plaintext or downgrade to v2. An implementation unable to offer TLS 1.3 reports `tls_unavailable` locally and does not connect.

Each installed desktop user has one long-lived P-256 ECDSA TLS server identity (`desktop_id`). Each Android installation has one long-lived P-256 ECDSA TLS client identity (`phone_id`). A peer ID is lowercase hex SHA-256 of the DER SubjectPublicKeyInfo (SPKI), exactly 64 ASCII characters. Both identities use locally generated X.509 certificates with `digitalSignature` key usage where the platform exposes that extension. Certificate renewal may keep the same key/SPKI; a changed SPKI is a changed identity. The application verifies the pinned SPKI, certificate validity dates, and any present key-usage/extended-key-usage extensions itself, because these private identities are not public CA identities. Reject absent or mismatched certificates, expired certificates, weak signature algorithms, inappropriate present usage extensions, and all other validation errors except the expected untrusted self-signed chain. An absent client EKU is permitted for Android Keystore generated self-signed certificates; pinning and TLS possession are mandatory. The desktop requires a client certificate on *both* sockets after pairing. TLS provides certificate proof of private-key possession and fresh per-connection authentication; there is no application-defined MAC, encryption, signature transcript, or key derivation. Disable TLS 0-RTT, if exposed. TLS session resumption must still provide the authenticated peer identity; otherwise disable resumption. Use operating-system cryptographic random generators for keys, capabilities, nonces, tickets, and session IDs.

The desktop display name is a user-editable label, not identity. Pairing UI displays the desktop name plus a grouped fingerprint derived from `desktop_id` (full value available in details). The phone's friendly name and `phone_id` are shown on Windows when approving or reviewing trust. Neither name participates in authentication.

### Protected storage

Android 10+ supports `AndroidKeyStore` `KeyPairGenerator` and `KeyGenParameterSpec`. Generate the client key with `ECGenParameterSpec("secp256r1")`, `PURPOSE_SIGN`, and SHA-256 digest; set certificate subject, serial, and validity explicitly. With signing purpose and no attestation challenge, Android documents a self-signed public-key certificate. The private key is nonexportable and must remain in `AndroidKeyStore`; never export it into a PKCS#12 file. Load the key/certificate chain from the Android Keystore alias through a `KeyManagerFactory` (or an alias-selecting `X509ExtendedKeyManager` backed by that `KeyStore`). Initialize a dedicated `SSLContext` with that key manager and a trust manager that pins the selected desktop SPKI; use it for both control and video `SSLSocket`s. The server must request the client certificate in TLS, and the phone must verify that it actually presented the expected alias and that the negotiated protocol is TLS 1.3. Android's `SSLContext` lists TLS 1.3 at API 29, the Android 10 baseline. A platform/provider failure to use the Keystore key for TLS is a pairing failure, never permission to copy the private key into app storage or omit client authentication.

Store the desktop SPKI/certificate, peer ID, name, timestamps, and revocation state in app-private storage encrypted with an Android Keystore AES-GCM key. Backups must exclude both this database and pairing state; losing keys requires re-pair. Do not require per-operation biometric authentication for the transport key: background recovery must work during an explicitly active phone session. A locked device still relies on OS storage protection and the visible foreground service/Stop action.

Windows 11 generates the server key as a persisted CNG P-256 key with `CngKeyCreationParameters` in the user store (`MachineKey` unset) and export policy `None`, then stores its certificate in `X509Store(StoreName.My, StoreLocation.CurrentUser)`. `SslStream.AuthenticateAsServerAsync` uses `SslServerAuthenticationOptions` with `ClientCertificateRequired=true` for paired control/video and rotation proof; its remote-certificate callback checks the full presented phone certificate against an active or rotation-pending SPKI before admitting any application message. The callback for the unauthenticated first `pair_init` connection is separate and never turns that connection into a trusted session. Store trusted phone SPKIs/certificates, labels, states, and expiry metadata in current-user app data protected with `ProtectedData`/DPAPI `DataProtectionScope.CurrentUser`, with user-only filesystem ACLs. Do not use machine-wide protection. Desktop identity replacement or lost Windows profile invalidates old trust and requires re-pair. Never log private keys, capabilities, tickets, or development secrets.

Platform references: [Android Keystore key generation](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder), [Android `KeyManagerFactory`](https://developer.android.com/reference/javax/net/ssl/KeyManagerFactory), [Android `SSLContext` and TLS 1.3 API level](https://developer.android.com/reference/javax/net/ssl/SSLContext), [.NET `SslStream` client authentication](https://learn.microsoft.com/en-us/dotnet/api/system.net.security.sslstream), [.NET server certificate validation callback](https://learn.microsoft.com/en-us/dotnet/api/system.net.security.sslserverauthenticationoptions.remotecertificatevalidationcallback), [CNG user-key options](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.cngkeycreationparameters.keycreationoptions), [CNG export policy](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.cngkeycreationparameters.exportpolicy), [Windows DPAPI user scope](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection).

## First pairing

1. The desktop user opens Pair. Windows generates a fresh 32-byte pairing capability `cap` and random 16-byte `pair_id`; it records only a hash of `cap`, creation time and expiry, and displays one QR. The QR is visible for at most 120 seconds. At most one active invitation exists per desktop user; opening a new one invalidates the old one. The desktop must show its real listening address and firewall state, not a discovery-advertised address.
2. The QR encodes a `camylla-pair://v3` URI with `host`, `control_port=58413`, `desktop_id`, `pair_id`, `cap`, and `expires_at` (UTC Unix seconds). UTF-8 URI length is at most 512 bytes; `host` is a DNS name of at most 253 ASCII bytes, bracketed IPv6 literal, or IPv4 literal. `cap` is 64 lowercase hex characters; `pair_id` is 32. The endpoint is a hint. The phone may replace it with a manually entered LAN address while retaining the scanned identity and capability. If scanning is unavailable, the Windows screen displays the same 256-bit capability as grouped base32 text plus the full desktop fingerprint for manual entry. Entering only an address or accepting a discovery result never authorizes pairing.
3. The phone user chooses Pair and scans the invitation. The scan authorizes pairing and automatically completes certificate proof without additional approval or Finish buttons. Manual invitation entry has one Pair action. It connects over TLS and pins the server SPKI to `desktop_id` **before** sending `cap`. An address redirect, discovery spoof, or wrong certificate fails before capability disclosure. The phone generates its Android Keystore identity before this step.
4. Over this pinned TLS connection, the phone sends `pair_init` with `pair_id`, `cap`, its client certificate (DER, base64), `phone_id`, and bounded friendly name. The desktop atomically compares capability hash, expiry, state, and pair ID, then marks the invitation **consumed before** responding. A second `pair_init`, even after interruption, receives `pair_consumed`; the user must open a fresh invitation. The desktop verifies that the supplied SPKI hashes to `phone_id` and requires the next TLS connection to prove possession through client-certificate authentication before committing trust. The pending `phone_id` may be accepted by the TLS validation callback **only** for this challenge, not as general trust.
5. Desktop responds `pair_challenge` with random 16-byte `challenge_id`, expiry at most 30 seconds, its current server certificate, and bounded desktop `name`. The phone opens a new pinned mutual-TLS control connection presenting its certificate and sends `pair_commit` with `pair_id` and `challenge_id`. Windows verifies the same phone certificate/SPKI, unexpired challenge, and the consumed invitation, then atomically stores phone trust and responds `pair_ok` containing both IDs. The phone commits desktop trust only after validating `pair_ok` on the same mutual-TLS connection. If the response is lost, either side may hold one-sided trust; a fresh invitation and re-pair replaces it. A consumed invitation is never restored after crash or timeout.

Pairing grants remembered trust only; it never authorizes capture or starts the camera. `pair_init` is allowed only on a dedicated pairing control TLS connection pinned by the QR, without a client certificate; all other unauthenticated message types are rejected. No pairing messages are accepted on the video listener. The desktop permits at most one pending challenge per invitation and five failed pairing attempts per source IP per 10 minutes, plus five globally per minute. Rate limiting is defense in depth, not identity; it may cause a visible `rate_limited` error and must not silently lengthen an authorization's lifetime. Do not log or echo the capability. Windows closes pairing listeners when Pair is dismissed or expired. The desktop user can cancel an invitation at any time. Opening the QR on the desktop and scanning it on the phone constitute pairing approval. Possession of this temporary capability permits one pairing within its expiry. Dismissing the QR cancels pending proof. Ordinary pairing never silently revokes another remembered identity; replacement and rotation retain explicit review.

## Repeat use and active session

Phone user explicitly taps Start for **each** capture authorization. Remembered trust, desktop UI actions, incoming connections, and recovery state cannot initiate capture. Android establishes mutual TLS on control, pinning `desktop_id`; Windows verifies `phone_id` is active. The phone sends `start` with `version=3`, `phone_id`, `client_nonce` (16 random bytes), `codec=h264`, bounded advertised modes, chosen mode and lens. Windows rejects unknown/stale identity or an existing active session, then generates random 16-byte `session_id`, 16-byte `server_nonce`, and 32-byte one-use `video_ticket`. It replies `started` with IDs, nonces, selected settings and ticket. The ticket is only ever sent on this authenticated control connection. Windows stores only a hash of the ticket. The session belongs to the authenticated `(desktop_id, phone_id)` pair and this live control connection, not the IP address.

Phone opens mutual TLS on video, pins the same desktop SPKI, and sends `bind` with version, `session_id`, both nonces, `phone_id`, and `video_ticket`. Windows accepts only when the client certificate matches the active control peer, the session and both nonces match, the control connection is live, the ticket is unused, and no video socket is bound. It atomically consumes the ticket, responds `ready`, and requests a fresh codec config/keyframe. A new video connection during recovery needs a *new* ticket obtained through `video_rebind` on the live control connection; the same session ID may remain. A control reconnect always retires the prior session and creates a fresh ID and nonces. Replayed or delayed `bind` messages cannot reattach to a new session. The video frame header's 16-byte session ID remains checked on every frame. A frame with an old ID, stale configuration generation, or wrong sequence is rejected/reset per v2 media rules.

`video_rebind` contains the active `session_id` and a new 16-byte `request_nonce`. The desktop first closes the old video socket, invalidates any outstanding ticket, and replies `video_ticket` with that same request nonce and a fresh 32-byte ticket expiring in 15 seconds. At most one outstanding ticket exists. A repeated request nonce is rejected; a delayed response with a different nonce is ignored by the phone. Recovery on a control-channel loss instead runs a new `start` with a fresh logical session. Tickets are never persisted.

The phone sends `stop` over control when the user taps Stop. Windows responds `stopped` if possible, immediately retires the session, tickets and bound video, and shows neutral output. Android stops capture/foreground service and cancels retries **without waiting for an acknowledgment**; transport failure cannot keep capture alive after local Stop. Desktop Exit and explicit desktop Stop likewise retire the session and close sockets; they cannot silently restart phone capture. A broken control connection retires its session on Windows. Android may retry a new authenticated control session only while its phone-started capture authorization remains active; it never persists that authorization across process death or explicit Stop. `ping`/`pong`, `sync`, and mode/configuration behavior retain v2 intent within v3 authenticated sessions.

## Revocation, rotation, and migration

Either side may revoke a remembered peer locally. Revocation immediately removes it from active authentication, retires matching sessions/tickets, and prevents automatic reconnect. A best-effort `peer_revoked` notice may be sent over a live authenticated control connection, but local revocation takes effect without delivery; the other side eventually shows `peer_revoked` and offers new pairing. Retain a bounded tombstone (`peer_id`, revoked time) for at least 30 days to prevent stale metadata import from reactivating a peer. A user may delete the tombstone after a fresh explicit pairing; never import trust from an old backup without the matching private key and a fresh confirmation.

Re-pair always requires a new invitation and explicit phone initiation, even if the presented `phone_id` is already known. On successful re-pair with the same identity, replace its metadata and clear any partial pairing state. If the phone presents a new identity for an existing named device, Windows must show the old and new fingerprints and require desktop confirmation; commit the new trust and revoke the old identity atomically. Phone likewise replaces the old desktop identity only after a fresh QR/manual authorization and visible confirmation. Re-pair never resumes a stopped capture session.

Certificate renewal using the same SPKI can replace the stored certificate after successful mutual TLS, provided it has valid usage and dates. A key/SPKI change follows this **idle-only** two-connection transaction; it cannot run while a capture session or video bind is active:

1. The rotating side generates a new nonexportable key/certificate but retains the old key. Over a mutual-TLS control connection authenticated with the **old** identities, it sends `rotate_offer` with `role` (`desktop` or `phone`), `old_id`, `new_id`, bounded `new_cert`, a random 16-byte `rotation_id`, and a 60-second deadline. Both applications show old/new fingerprints. The phone user explicitly confirms every rotation; the desktop user also confirms a phone-key replacement. A revoked old identity cannot offer or approve rotation. Only one rotation may be pending per desktop; pairing and Start are unavailable while pending.
2. The existing video port 58414 becomes an exclusive **rotation proof** endpoint for the 60-second pending interval; it accepts no `bind` or media. For `role=desktop`, Windows presents the *new* server certificate on this port while still serving the old certificate on the existing control connection. The phone verifies the proof socket's TLS server SPKI equals offered `new_id`, presents its currently trusted client certificate, and sends `rotate_prove`. For `role=phone`, Windows presents its currently trusted server certificate and accepts only the offered *new* client certificate on the proof socket. This is TLS private-key possession by the rotated party, not a signature over a homemade challenge. `rotate_prove` contains `rotation_id`, `role`, `old_id`, and `new_id`; the receiver matches it to the pending offer, TLS certificate, and old authenticated control connection, then responds `rotate_ready`. Proof TLS handshake retains the 1.5-second transport timeout; its record has a five-second read timeout. No media is accepted. The proof endpoint is the existing firewall-open video port; no new inbound port or discovery trust is needed.
3. After `rotate_ready`, the phone sends `rotate_commit` with `rotation_id` over the **old** authenticated control connection. Windows durably commits new peer trust or its own new server identity and revokes the old identity, sends `rotate_ok` on that already authenticated connection if possible, then closes proof/control sockets. The phone commits its new trust only after `rotate_ok` or a successful post-commit control TLS probe against `new_id`; it must never treat `rotate_ready` alone as final. The proof and commit IDs are single-use and recorded with the transaction so replay cannot change trust twice. After a committed desktop rotation, both listeners use the new server certificate and the old key is retired/deleted; after a committed phone rotation, Windows accepts only the new phone SPKI.

If the offer/proof/commit times out before the durable Windows commit, discard the candidate and continue using the old identity. If `rotate_ok` is lost, the phone probes the normal control port using the proposed identity: for `role=desktop`, it pins the **new desktop SPKI** and presents its still-current phone certificate; for `role=phone`, it pins the still-current desktop SPKI and presents its **new phone certificate**. A successful mutual-TLS probe means Windows committed and the phone can commit locally, then query `rotation_status` under that new authenticated pair. If the old identity still answers, the phone instead queries `rotation_status` on a freshly authenticated old-identity control connection and may retry `rotate_commit` only when Windows says `ready`. The pre-commit proof and pending transaction must survive such a control reconnect until the 60-second deadline; it remains idle-only. Windows retains a bounded committed transaction result for 24 hours so a status query under the new identity returns `committed` without reactivating the old identity; if no authenticated recovery path works, show mismatch and require fresh pairing. No old-key fallback is offered after durable commit. Desktop rotation also updates the QR identity. Compromised remembered credentials cannot be repaired by an unconfirmed in-band offer: revoke and re-pair through a newly displayed invitation.

`rotation_state.state` is `ready`, `committed`, or `expired`. `ready` is returned only under the old authenticated identity while its deadline remains live; `committed` only under the new identity, and `expired` under the old identity if it is still trusted. A status query from an unrelated or revoked peer gets `untrusted_peer`. The candidate key and proof listener are removed on expiry/cancel; a committed result record contains IDs and status only, no private key or capability.

Production builds never read `Camylla/m3-proof` certificate/secret files or Android M3 pin/secret fields. No automatic conversion from the M3 secret to production trust. On first production launch, show a one-time migration explanation and require fresh pairing; remove the M3 secret, certificate/private key and any cached Android values after explicit upgrade/cleanup. Development tools may retain a clearly labelled separate M3 mode, disabled in production packages. A v3 peer rejects v2 major version and does not fall back after a failed v3 attempt.

## Wire grammar and failure handling

Use v2's four-byte big-endian length prefix and strict UTF-8 JSON for control and initial video bind records. Payload length is 1–4096 bytes before allocation; nesting depth at most 4; no duplicate keys, unknown required fields, or trailing data. All `type` values are ASCII lower snake case, at most 32 bytes. Hex values are lowercase and fixed length. Names are NFC UTF-8, 1–64 bytes, with control characters rejected. Certificates are DER base64, at most 2048 encoded bytes. Modes list has 1–16 values, each at most 32 bytes. Reject unsupported major versions; ignore only explicitly marked optional minor-version fields. Set a 1.5-second TLS handshake timeout, 5-second read timeout for each handshake/pairing record, and a maximum of one in-flight request per connection. Video access-unit framing and 4 MiB bound remain as in v2, with the major byte set to 3; v2 decoders reject it.

Every error record is `{ "type":"error", "version":3, "code":"..." }` and closes the affected connection unless noted. Codes: `unsupported_version`, `invalid_record`, `identity_mismatch`, `pair_expired`, `pair_consumed`, `pair_rejected`, `rate_limited`, `untrusted_peer`, `peer_revoked`, `session_busy`, `stale_session`, `bind_rejected`, `mode_unsupported`, `tls_unavailable`. For an unauthenticated peer, do not reveal whether an identity/capability exists: send generic `pair_rejected` or close. TLS failures may close without JSON. No error includes secrets, certificates, or raw user data. Time comparisons for invitation expiry use Windows wall clock against absolute UTC and a monotonic timer since creation; expire when **either** reaches its limit, so clock rollback cannot extend the invitation. Pairing challenge expires after 30 monotonic seconds. A session has no absolute lifetime while its authenticated control channel and phone authorization remain live, but heartbeat timeout retires it. Tickets expire after 15 monotonic seconds and on any control/session retirement.

Example records (illustrative placeholders, not usable secrets):

State transitions: desktop `unpaired -> invitation -> challenge -> paired -> active -> paired`; cancellation/expiry/interruption from invitation or challenge returns to `unpaired` with consumed/invalid invitation. `active -> paired` on Stop, control loss or heartbeat timeout. `paired/active -> revoked` on local revocation. Idle `paired -> rotation_pending -> paired(new ID)` only after proof and durable commit; timeout returns to `paired(old ID)`. `paired -> paired` on same-key certificate renewal. Android `unpaired -> pairing -> paired -> starting -> streaming/recovering -> paired` on Stop; it never transitions from paired to capture without local Start. An interrupted pairing may leave one-sided trust, detected on the next Start and repaired by fresh pairing.

## Threat and failure review / tests

| Threat or failure | Required behavior and automated test |
| --- | --- |
| Malicious LAN peer, discovery/address spoof | Wrong desktop SPKI fails before `cap`; untrusted client cannot `start` or bind; fuzz malformed lengths/JSON before allocation. |
| QR reuse or stolen stale payload | Atomic one-use consumption, 120-second expiry, cancel invalidation, and rate limits; replay fails after interruption and after receiver restart. |
| Intercepted current QR | Physical-display secrecy is limited; desktop candidate confirmation and short expiry mitigate; stolen active QR can race, so UI must identify the phone before commit. |
| Stale video bind/session | Old ticket/ID/nonce, second concurrent bind, wrong client SPKI, expired ticket, and bind after control close all fail. |
| Compromised remembered key | Attacker can authenticate as that peer until local revocation; revoke retires active session, rotation requires phone confirmation, new QR re-pair recovers. |
| Revoked peer / restored backup | Tombstone prevents stale trust import; revoked client TLS never enters active session. |
| Interrupted pairing or rotation | Consumed invitation does not revive; partial trust is surfaced and repaired with a new QR; uncommitted rotation retains old identity. |
| Rotated desktop key spoof / stale proof | The proof socket on port 58414 must present exactly the offered new SPKI during the pending window; wrong certificate, role, ID, old control peer, deadline, or repeated proof fails. |
| Lost `rotate_ok` / crash at commit | Probe new identity and query old authenticated `rotation_status` as applicable; durable commit is all-or-nothing, old key is never reactivated after commit, and mismatch prompts re-pair. |
| Android TLS client identity unavailable | Pairing/Start fails closed if the nonexportable Keystore key cannot be offered by a key manager or Windows does not verify its TLS certificate; no export or secret-only fallback. |
| Phone Stop during outage | Capture and retry stop locally immediately; later packets/tickets cannot reactivate the old session. |
| Clock rollback / expiry | Invitation expires by both UTC and monotonic deadlines; challenge/ticket use monotonic deadlines; boundary tests at expiry. |
| Lost video socket | Fresh `video_rebind` ticket on live control only, then sync frame; no stale queued frames replayed. |

Implementation tests should cover both Android and Windows parsers/state machines, real TLS mutual-auth against generated test identities, certificate replacement/revocation, persistence under user scope, and incompatible v2/v3 attempts. A required #25 integration acceptance test uses a real Android 10+ device (including the S21 Ultra target): generate a nonexportable Android Keystore P-256 identity, present it through the selected `KeyManager`/`SSLContext` to Windows `SslStream` on **both control and video sockets**, verify pinned server and client SPKIs, then reconnect both sockets and restart both apps using persisted trust. Repeat with missing/revoked/expired client keys and wrong server pin; each must fail closed without exporting the key or falling back to the M3 secret. Record Android version, TLS version, certificate and KeyManager provider behavior, and Windows build. Physical S21 Ultra/Windows firewall and manual-address UX validation belongs to M4.4; this specification alone claims no device pass.

## Implementation additions for changed identity and interrupted rotation

`pair_challenge` also carries `requires_approval` (boolean) and
`previous_phone_id` (null for ordinary pairing, previous 64-character SPKI ID
for a same-name identity replacement). Friendly names are only a prompt to
review a possible replacement, never proof of identity. Windows displays old
and new fingerprints and requires approval before atomically revoking the old
identity and committing the new one. Android waits automatically using a
mutual-TLS `pair_status` record with `pair_id` and `challenge_id`;
`pair_state` returns `challenge_id` and state `awaiting_approval` or `approved`.
The same 30-second challenge deadline applies. Ordinary QR pairing needs no
additional approval and closes the PC QR dialog on successful commit.

Rotation status may be `awaiting_approval`, `approved`, `ready`, `committed`,
or `expired`. The phone's Resume action probes the proposed identity first.
Explicit Repair pairing revokes all locally saved PCs, clears the pending
transaction atomically, and requires a fresh QR. For a pending phone-key change
it retains the proposed nonexportable key and retires the previous key after
local persistence, avoiding an old-key fallback when remote commit is uncertain.
Neither resume nor repair starts capture.
